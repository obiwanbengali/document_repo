BN Design at Scale: Build Approaches, Routing and Inference Orchestration

Context: ~850 NHS Pathways pathways, usage following a power-law distribution (small number of pathways carry the majority of call volume, long tail of lightly-used pathways). Target: millions of triages per annum. Building individual networks is tractable — the open problem is inference-time orchestration: which BN(s) to load, how to run them together, and how to avoid re-asking the patient questions already answered when moving between BNs.

Part 2 — Entry and Routing Strategies

Before any BN runs, the system must decide which BN(s) are candidates given the presenting symptom(s). Four viable strategies, not mutually exclusive.

Option A — Static symptom-group entry (inherited from current Pathways)

Reuse the existing NHS Pathways presenting-complaint categorisation as the first filter. Each presenting complaint category maps to a fixed shortlist of BNs.

flowchart LR U["Patient / Call Handler\npresenting complaint"] --> SG["Static Symptom Group\nLookup Table\n(inherited from Pathways)"] SG --> L["Shortlist of BNs\nfor this symptom group\n(fixed at build time)"] L --> BN1["Tier 1 BN"] L --> BN2["Tier 2 Family BN"] L --> BN3["Tier 3 Template BN"]

Pros: Zero additional build effort — reuses existing categorisation; deterministic and auditable; fast (a lookup, not a model).
Cons: Inherits any weaknesses of the current category boundaries; does not adapt as new evidence arrives; cannot handle multi-symptom presentations gracefully.

Option B — Retrieval-based initial evaluator

Each BN is tagged at build time with the SNOMED concepts / symptoms it covers (this is a natural by-product of the Layer 1/2/3 ontology work already done). At session start, presenting symptom(s) are matched against this BN metadata index to retrieve all BNs whose scope includes the presenting symptom — not just one predetermined group.

flowchart LR U["Patient presenting\nsymptom(s)"] --> EMB["Symptom-to-Concept\nMapping (SNOMED)"] EMB --> IDX[("BN Metadata Index\nconcept coverage per BN\nbuilt at model registration time")] IDX --> CAND["Candidate BN Set\nALL BNs whose scope\nincludes this concept"] CAND --> BN1["Tier 1 BN"] CAND --> BN2["Tier 1 BN"] CAND --> BN3["Tier 2 Family BN"] CAND --> BNn["... N candidates"]

This is what you described: "an initial evaluator that would take given symptoms and bring all possible BNs that had those symptoms." The BN metadata index is a natural extension of the model registry — every registered model carries a manifest of the concepts it covers.

Pros: Adapts automatically as new BNs are registered — no manual symptom-group maintenance; captures multi-symptom presentations naturally (a candidate set, not a single bucket); directly reusable for Tier 2/3 as they are built.
Cons: Candidate sets can be large for common symptoms (e.g. "chest pain" may match 15+ BNs) — this is exactly the scale problem Part 3 addresses; requires the concept-coverage metadata to be well maintained and versioned.

Option C — Two-stage probabilistic router

An intake router narrows to a small candidate set, then a family disambiguation router commits to one specific BN after 2–4 high-information questions.

flowchart TB U["Patient presenting\nsymptom(s)"] --> SA["Stage A — Intake Router\n(pathway ID + early answers)"] SA -->|"high confidence"| PB["Route directly\nto Pathway BN"] SA -->|"ambiguous"| SB["Stage B — Family\nDisambiguation Router\n(2-4 more questions)"] SB -->|"commits"| FB["Route to specific\nPathway or Family BN"] SB -->|"still uncertain"| SC["Stage C — Safety Fallback\nconservative disposition\nor escalation"]

Pros: Bounded computation — commits to one BN quickly; safety fallback is explicit and built in.
Cons: Requires empirically calibrated confidence thresholds (T1/T2) — cannot be set by design alone; a hard commit can be wrong if the router misjudges early.

Option D — Hybrid: static category first, retrieval within category

Use Option A to narrow to a broad category cheaply (deterministic, fast, zero cost), then apply Option B's retrieval only within that category to build the candidate set. This bounds candidate set size while retaining adaptability.

flowchart LR U["Presenting symptom"] --> SG["Static category filter\n(cheap, deterministic)"] SG --> RET["Retrieval within category\n(concept-coverage index)"] RET --> CAND["Bounded candidate set\ntypically 3-8 BNs"]

Recommendation: Option D. It bounds the candidate set size (solving Option B's scale weakness) while remaining adaptive (solving Option A's rigidity). Feeds directly into the orchestration patterns below.

Part 3 — Inference Orchestration Patterns (the core problem)

Once a candidate BN set exists, how do you actually run inference across them at a rate of millions of sessions per year? Four patterns, increasing in sophistication.

Pattern 1 — Strict single-path commit

The router commits to exactly one BN before any inference runs. Simplest possible architecture.

sequenceDiagram participant P as Patient participant R as Router participant BN as Committed BN P->>R: presenting symptom R->>R: select single BN (Option A/C) R->>BN: load BN, begin session loop each question P->>BN: answer BN->>BN: update posterior end BN->>P: disposition

Compute cost: Lowest — one BN active per session.
Scale characteristic: Trivially horizontal — each session is independent, one model in memory.
Risk: Misrouting is invisible until too late; no cross-checking; wrong disposition if the wrong BN was committed to early.
Verdict: Cheapest at scale but carries the highest clinical risk. Only acceptable if the router's confidence is very high (Stage A direct route in Option C).

Pattern 2 — Parallel candidate shortlist evaluation ("beam" pattern)

Load the top-N candidate BNs simultaneously. Feed the same evidence to all of them. After each answer, drop candidates whose posterior confidence falls below a pruning threshold. Continue until one candidate dominates or the shortlist collapses to one.

sequenceDiagram participant P as Patient participant O as Orchestrator participant BN1 as Candidate BN 1 participant BN2 as Candidate BN 2 participant BN3 as Candidate BN 3 P->>O: presenting symptom O->>O: retrieve candidates (Option B/D) O->>BN1: init with shared evidence O->>BN2: init with shared evidence O->>BN3: init with shared evidence loop each question (shared across active candidates) P->>O: answer O->>BN1: evidence update O->>BN2: evidence update O->>BN3: evidence update BN1-->>O: posterior BN2-->>O: posterior BN3-->>O: posterior O->>O: prune candidates below threshold end Note over O: BN2 dominates, BN1 and BN3 dropped O->>P: disposition (from BN2)

Compute cost: N× a single BN while candidates are active; drops as pruning proceeds — most expensive at session start, cheapest by the end.
Scale characteristic: Compute cost is front-loaded and self-limiting (pruning reduces load quickly, typically within 2–3 questions). Still meaningfully more expensive than Pattern 1 at the start of every session — at millions of sessions/year this matters.
Safety benefit: No hard early commit — the correct BN survives on its own evidence-driven merit, not a single router decision.
Verdict: Best safety profile of the four patterns. The cost is manageable if pruning is aggressive and candidate sets are bounded (Option D keeps this to 3–8 candidates).

Pattern 3 — Composite shared-core with subnet activation

Rather than running N separate BN objects, build one composite graph: a shared Layer 1/2 core plus "subnets" for each candidate pathway's Layer 3 variables. Subnets are activated or deactivated as evidence makes them more or less plausible.

flowchart TB subgraph Composite["Composite Session Graph"] Core["Shared Core\n(Layer 1 concepts:\ndemographics, hemodynamic\nstability, red flags)"] Fam["Shared Family Layer\n(Layer 2 concepts:\nchest pain family variables)"] Sub1["Subnet: Pathway A\n(Layer 3, ACTIVE)"] Sub2["Subnet: Pathway B\n(Layer 3, ACTIVE)"] Sub3["Subnet: Pathway C\n(Layer 3, DEACTIVATED\nlow posterior)"] Core --> Fam Fam --> Sub1 Fam --> Sub2 Fam -.deactivated as evidence rules it out.-> Sub3 end

Compute cost: Lower than Pattern 2 for shared concepts (evaluated once, not N times); subnets only add incremental cost for their pathway-specific variables.
Scale characteristic: More efficient than Pattern 2 because shared evidence is computed once instead of redundantly across N separate BN objects.
Complexity cost: Significantly harder to build and validate — the composite graph structure must be assembled dynamically per session, and clinical review of a dynamically-composed graph is harder than reviewing N fixed graphs.
Verdict: The most computationally elegant solution, but the engineering and clinical governance overhead is substantial. Best suited to Tier 2 family BNs where the shared Layer 2 core is already a formal, validated artefact — less suited to ad hoc composition across arbitrary Tier 1 pathways.

Pattern 4 — Orchestrator + stateless inference worker pool (scale pattern)

This is not a competing inference logic pattern — it is the deployment architecture that makes Patterns 1–3 viable at millions of sessions per year. Separate session/evidence orchestration from BN inference computation.

flowchart TB subgraph Client P["Patient / 111 Online\nor Telephony"] end subgraph Orchestration["Session Orchestrator (stateful)"] SO["Session Orchestrator\nholds: evidence, candidate set,\nposteriors, routing state"] SS[("Session Store\nRedis / DynamoDB\nconcept-keyed evidence")] SO <--> SS end subgraph Workers["Stateless BN Inference Worker Pool (horizontally scaled)"] W1["Worker: evaluate BN X\ngiven evidence"] W2["Worker: evaluate BN Y\ngiven evidence"] W3["Worker: evaluate BN Z\ngiven evidence"] end MR[("Model Registry\nversioned BN packages")] P <--> SO SO -->|"dispatch evaluation requests"| W1 SO -->|"dispatch evaluation requests"| W2 SO -->|"dispatch evaluation requests"| W3 W1 -->|"posterior"| SO W2 -->|"posterior"| SO W3 -->|"posterior"| SO W1 -.loads model from.-> MR W2 -.loads model from.-> MR W3 -.loads model from.-> MR

Why this matters at scale: BN inference workers are stateless and only need the evidence set plus a model version to compute a posterior — they can be scaled horizontally like any stateless compute service (containers, serverless functions). The Session Orchestrator is the only stateful component and its job is narrow: hold evidence, dispatch evaluation requests to workers, aggregate posteriors, apply pruning/routing logic.

This deployment pattern is compatible with any of Patterns 1–3 as the inference logic running inside it. Pattern 2 (parallel candidates) simply means the orchestrator dispatches to N workers instead of 1 per question round.

Verdict: This is the necessary infrastructure pattern regardless of which inference logic pattern is chosen, once volume reaches millions/year. Should be adopted as the baseline deployment architecture.

Part 4 — Cross-BN Session State Reuse (avoiding repeat questions)

This is the requirement that ties everything together: if the router or shortlist-pruning process switches from BN_A to BN_B, the patient must not be re-asked a question they already answered, provided the same clinical concept is relevant to BN_B.

The core mechanism: concept-keyed evidence, not variable-keyed evidence

The critical design decision is that the session evidence store is not keyed by BN-specific variable names (Respiratory_Status, Chest_Pain_Characteristics). It is keyed by the underlying SNOMED concept the answer represents. Each BN then projects the shared concept-keyed evidence into its own variable space using the mapping table that the three-layer ontology already requires.

flowchart TB subgraph Global["Global Session Evidence Store (concept-keyed)"] E1["SNOMED concept: 267036007\n(dyspnoea) = Present"] E2["SNOMED concept: 29857009\n(chest pain) = Moderate"] E3["SNOMED concept: 271594007\n(respiratory rate) = Elevated"] end subgraph ProjA["BN_A view (Tier 1 — PA212)"] VA1["Respiratory_Status\n(derived from E1 + E3)"] VA2["Chest_Pain_Characteristics\n(derived from E2)"] end subgraph ProjB["BN_B view (Tier 1 — different pathway,\nsame chest-pain family)"] VB1["Breathlessness_Severity\n(derived from E1)"] VB2["Pain_Score\n(derived from E2)"] VB3["New_Variable_Only_In_B\n(NOT YET ANSWERED)"] end Global -->|"concept-to-variable\nmapping (Layer 1/2 ontology)"| ProjA Global -->|"concept-to-variable\nmapping (Layer 1/2 ontology)"| ProjB

When the orchestrator switches focus from BN_A to BN_B (during Pattern 2 pruning, or after a Pattern 1 misroute correction), it does not start a fresh evidence set. It re-projects the existing global evidence into BN_B's variable space. Only variables in BN_B that have no corresponding concept yet in the global store (New_Variable_Only_In_B above) trigger a new question to the patient.

Sequence: switching BNs mid-session without repeat questions

sequenceDiagram participant P as Patient participant O as Orchestrator participant GS as Global Evidence Store (concept-keyed) participant BNa as BN_A (active) participant BNb as BN_B (candidate, not yet active) P->>O: answers Q1 (dyspnoea = present) O->>GS: store {concept: dyspnoea, value: present} O->>BNa: project evidence, update posterior BNa-->>O: posterior_A P->>O: answers Q2 (chest pain = moderate) O->>GS: store {concept: chest_pain, value: moderate} O->>BNa: project evidence, update posterior BNa-->>O: posterior_A (confidence dropping) Note over O: Pattern 2 pruning suggests BN_B is now more plausible O->>BNb: activate, project EXISTING global evidence (dyspnoea, chest_pain already known) BNb-->>O: posterior_B (computed WITHOUT re-asking Q1/Q2) Note over O: BN_B has one variable with no mapped concept yet O->>P: ask ONLY the new question BN_B needs P->>O: answers Q3 O->>GS: store {concept: new_concept, value: X} O->>BNb: project evidence, update posterior BNb-->>O: posterior_B (final) O->>P: disposition

What this requires to work

RequirementWhy
Every BN variable must have a documented concept mappingWithout this mapping, projection between BNs is impossible
Layer 1/2 ontology governance must be enforced rigorouslyIf two BNs map the same real-world concept to different granularity or meaning, projected evidence will be silently wrong
The global evidence store must be the source of truth; BN-specific evidence sets are always derived, never independently collectedPrevents state divergence between BN_A's view and BN_B's view of the same patient
Concept-to-variable mapping must be versioned alongside each BN model packageIf a BN's mapping changes between versions, historical session replay and cross-BN projection must know which mapping version applied
Contradictory concept values across time must be handled explicitly (e.g. if two different-worded questions somehow map to the same concept with different apparent answers)Contradictory evidence flag

This mechanism is what makes Pattern 2 (parallel candidates) and Pattern 3 (composite core) affordable in terms of patient experience — the computational cost of running multiple BNs is hidden entirely from the patient, who only ever sees the next most-informative unanswered question, regardless of how many candidate BNs are active behind the scenes.

Open Decisions Requiring Empirical Calibration

These cannot be resolved by architecture alone — they require retrospective data (Candidate 1/1b from the validation candidates document) to calibrate:

  1. Candidate set size bound for Option D — how many BNs is "too many" before Pattern 2's front-loaded compute cost becomes a real capacity problem at millions of sessions/year
  2. Pruning threshold — at what posterior confidence gap does a candidate get dropped from the shortlist in Pattern 2
  3. Pattern 2 vs Pattern 1 cutover point — is there a volume or acuity threshold below which Tier 2 pathways should also use Pattern 1 for cost reasons
  4. Concept mapping granularity — how finely SNOMED concepts must be split to avoid false evidence reuse across BNs that use "the same" concept at different clinical resolution
  5. Worker pool sizing and autoscaling policy for Pattern 4 against real session volume and concurrency patterns
  6. Composite graph governance model (Pattern 3) — what clinical review process is required for a dynamically-assembled graph, given the existing three-gate review process assumes a fixed graph per BN
