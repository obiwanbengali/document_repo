Architecture Feasibility & Comparison

Comparing architectures

"How large, fast, scalable and costly would the candidate architectures be?"

Phases 1 and 2 established what the estate contains and where its natural boundaries might lie. Architecture Feasibility & Comparison asks the question that decides the design: are the candidate architectures different enough, in size, speed, operability or cost, for the choice to be made on technical grounds?

Three options are compared on identical terms — one model following the content as written, one model with duplicate questions represented once, and several smaller models based on the Candidate Family Discovery candidate families.

    Important caveat on everything below

    Architecture Feasibility & Comparison uses the Candidate Family Discovery candidate families as a provisional analytical baseline. Those families have not been through clinical review. Every figure on this page relating to several smaller models inherits that caveat, and will change once the family boundaries are settled clinically.

    Representation sizing

    How large would each option be?

    The three options differ in one respect only: what counts as the same question appearing more than once. The same clinical question can appear in dozens of pathways, so that single choice changes the size of the model by more than anything else in this analysis.

    CPT growth

    How much probability data would each option hold?

    A Bayesian model does not just hold variables; it holds a number for every combination of a variable's answers and the answers of the variables it depends on. Add one more dependency and that table multiplies in size rather than adding to it.

    How many dependencies each variable would have is a clinical modelling decision that has not been taken. The figures below therefore span a deliberate range rather than offering a single estimate.

    Inference benchmarking

    How fast would each option answer?

    Models were built and timed for each option under controlled conditions. The important qualifier is how much of a real model each tested model represented — stated on the chart, because it governs how far the timings can be trusted.

    Runtime architecture

    How would each option actually be deployed?

    "Several smaller models" is a statement about the model, not about the running system. Those models could sit inside a single service, or be spread across many. Four deployment patterns are carried forward so that cost and operational risk attach to a concrete shape.

    Infrastructure & cost

    What would each option cost to run?

    Modelled monthly compute cost for each deployment pattern, across a range of assessment volumes. These are scenarios built on stated assumptions, intended for comparing the patterns against each other.

    Every option has a genuine strength and a genuine price for it. Presented side by side so the trade-off is explicit rather than buried in a recommendation.
